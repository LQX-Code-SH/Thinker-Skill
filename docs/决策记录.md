## D-001 运行期拓扑：编排在外部，执行在本体

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 编排在设计期于**机器人外主机**完成，组合成工作流或 Agent 后，将配置与代码下发到**机器人本体**执行。运行期不存在跨网络调用 |
| 依据 | 业务方确认；`kaiwu.yaml` 的 `mcp_cfg.url` 默认为 `http://localhost:8000/mcp`，印证 Agent 亦运行在本体 |
| 影响 | 见下 |

### 三阶段模型

```
① 编排期（外部主机） 技能能力快照 + 编排 → workflow / agent 配置 / 技能包
② 部署期（机器人）   安装技能包，校验产物引用的技能与版本
③ 运行期（机器人）   工作流引擎 →Action→ ┐
                    LLM Agent  →MCP(localhost)→ ┴→ skill_runtime → Pipeline → 身体
```

### 由此确定的结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | 运行时不存在跨网络调用 | 执行在本体 |
| 2 | **ROS Action 是运行时主接口**，且为稳定契约 | 工作流产物在编排期引用技能，部署后运行时依赖它 |
| 3 | MCP 定位收窄为「LLM Agent 的工具层」，同为稳定契约 | 服务对象是 LLM 的自描述与动态选工具，不承担确定性工作流 |
| 4 | 编排期只需要「技能能力快照」，不需要实时接口 | 外部主机只需知道有哪些技能与参数 schema |
| 5 | 确定性工作流不走 MCP | 同机直接 Action，避免 MCP 的取消不可靠与请求级超时限制 |

### 被削弱的原有担忧

| 担忧 | 结论 |
|---|---|
| MCP 300s 时限约束 | 确定性工作流不走 MCP，不受影响；仅约束 Agent 的工具调用 |
| MCP 取消依赖客户端实现 | 同上；工作流侧的取消由 Action 保证 |
| 跨网络鉴权 / 端口管理 | 不跨网络，降级为本机 `localhost` 问题 |

### 接口稳定性承诺（修正此前建议）

| 接口 | 承诺 | 服务对象 |
|---|---|---|
| `/thinker/skill/<skill>/action` | **稳定契约** | 本机工作流引擎 |
| MCP tool | **稳定契约** | 本机 LLM Agent |
| `thinker/ControlCommand` Service | 不承诺 | 调试 |
| ROS topic / 内部 srv | 不承诺 | 技能内部 IPC |

> 修正：此前建议「把 Action 降级为不承诺的内部接口」在此模型下不成立 —— 工作流产物引用技能，运行时必须依赖 Action 稳定。两条接口是对等契约，只是作用域不同。

### 衍生待澄清问题

| 编号 | 问题 | 状态 |
|---|---|---|
| Q-001 | 部署产物的形态（BT XML / YAML 步骤 / 生成代码）与校验时机（部署期预检 vs 启动拒启） | 暂缓（见 D-002） |
| Q-002 | 编排期如何获取技能能力快照：仓库导出 / 机器人上报 / 主动推送 | 暂缓（见 D-002） |
| Q-003 | 产物引用技能名+版本，还是直接引用 Action 名 | 接口名已冻结，产物格式暂缓 |
| Q-004 | 「下载代码」的边界：技能安装包 vs 用户工作流脚本，是否允许 import `core` 内部模块 | 技能包属 v1；用户脚本暂缓 |

## D-002 阶段划分：先技能与调用，上层编排后置

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 当前不存在工作流编排方案与编排工具。v1 范围收敛为「技能实现 + 技能调用」；工作流引擎、产物格式、编排期校验、能力快照全部推迟到上层应用阶段 |
| 依据 | 业务方确认 |

### 影响

| # | 影响 |
|---|---|
| 1 | 不实现工作流引擎，不定义工作流产物格式，不实现编排期校验器 |
| 2 | 但接口现在就必须稳定：MCP tool 与 `/thinker/skill/<skill>/action` 是未来编排的引用目标 |
| 3 | `Skill.action` 定为**通用型**（goal 带技能名 + `params_json`）；typed action 生成能力推迟到编排器出现时再定 |
| 4 | 参数 schema 的唯一事实源是 **MCP 工具的函数签名与类型注解**，不在 `skill.yaml` 中重复定义；未来需要编排期校验时，用导出脚本从签名生成 |
| 5 | 技能离线安装包（`pack_skill.sh`）仍属 v1 范围 —— 它服务的是"技能下发"本身，与工作流编排无关 |

### 何时必须回来处理

- 出现第一个真实工作流需求
- 需要让非开发者（产品/现场）编排流程
- 技能数量超过约 10 个、靠人工记忆组合关系开始出错

### 里程碑（M0~M4）

| 阶段 | 内容 | 验收 |
|---|---|---|
| M0 | 协议 + `skill_sdk` + `skill_core` 最小实现 + mock 技能 + 双接口壳 | 开发机用 `FakeBody` 跑通 MCP/Action → runtime → pipeline → feedback；Action 可 cancel |
| M1 | 感知类技能：`detect_object`（不改身体，风险最小） | 感知链路真机可用 + 全部失败分支带 `code` |
| M2 | 操作类技能：`fetch_object` + 聚合器 | 真机抓取成功；经聚合端口被 kaiwu-agent 调通 |
| M3 | 类别扩容：`navigation` / `speech` / `camera` | 各类别至少 1 个技能跑通；同机 ≥3 技能共存 |
| M4 | 离线安装包与卸载 | `pack_skill.sh` / `install_skill.sh` 一键装/卸；卸载后其余技能正常 |
| 后置（v1.1+） | 工作流引擎、编排器、`scene/`、typed action、任务队列 | 见上文「何时必须回来处理」 |

### v1 范围（据此收敛）

```
core/interfaces   ControlCommand.srv + Skill.action + msg
core/common       DataBuffer / TransformUtil / ConfigLoader / logger / TTS
core/sensor        感知数据通道（相机 / RGB-D / TF）
core/body         控制器 / QP / moveit / 腰 / 头 / 手爪 / 导航 / tf
core/skill_core   registry / runtime / pipeline / body_arbiter / 两个 frontend
skills/<类别>/…   至少一个真技能端到端（fetch_object）+ 一个 mock 技能
python/           thinker_mcp_bridge + thinker_mcp_aggregator
tools/            pack_skill.sh（离线安装包）
```

不含：工作流引擎、编排器、编排期校验、能力快照、typed action、任务级队列。

## D-003 信封扩展：错误码 + 可重试标记

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 统一信封在 `state`/`msg` 基础上增加 `code`（枚举）与 `retryable`（布尔），业务字段统一收进 `data`。不设 `category`，类别由 `code` 前缀派生 |
| 依据 | `msg` 是给 LLM 的中文话术，程序无法解析；`code` 一旦晚加，需改动所有技能返回值 |

### 最终信封

```json
{"state": "succeed|failed|cancelled", "code": "MOTION_GRASP_FAILED",
 "msg": "抓取失败", "retryable": true, "data": {"object_name": "bottle"}}
```

| 字段 | 消费者 | 说明 |
|---|---|---|
| `state` | 两者 | 三值，新增 `cancelled` |
| `code` | 程序 | 大写蛇形枚举，前缀即类别；成功为 `OK` |
| `msg` | LLM / TTS | 按 `code` 从 `configs/errors.yaml` 模板生成 |
| `retryable` | 程序 | 仅 `failed` 时有意义 |
| `data` | 两者 | 业务附加字段统一收进来，不再顶层乱扩 |

### 配套机制

| # | 机制 |
|---|---|
| 1 | 技能只产出 `code`，不手拼 `msg`；`msg` 由 `skill_runtime` 出口按 `configs/errors.yaml` 模板 + `msg_params` 生成 |
| 2 | 参考实现的 `return_msgs.*` 改以 `code` 为 key，与错误码表合流 |
| 3 | `skill.yaml` 增加 `errors:` 声明本技能可能产出的 code |
| 4 | `tests/test_error_codes.py` 校验：表与配置一致、技能声明的 code 均存在、无未声明 code 被抛出 |

### 未采纳

| 方案 | 原因 |
|---|---|
| 只加 `code` | 编排侧仍需自行推断可重试性，容易各处判断不一致 |
| 加 `category` 字段 | 与 `code` 前缀重复，存在不一致风险 |

## D-004 技能编排契约：声明式 Step 列表

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 技能只产出 `Step` 列表，不直接操作 Pipeline；Pipeline 负责 tick 驱动、超时、重试、进度与失败处理 |
| 依据 | 参考实现的 `(callable, "描述串")` 元组把展示文案与流程控制耦合（前缀匹配决定是否执行），改一个字可能改变执行路径 |

### 关键澄清

声明式的是**步骤结构**，不是**执行方式**。运控必须每 tick 持续下发目标（参考实现 QP 循环下发 20×0.04s），因此 `Step.run` 仍是每 tick 调用一次的 tick 函数。

### 契约

```python
@dataclass
class Step:
    name: str                    # 唯一阶段名 → feedback.phase
    run: Callable[[StepCtx], StepResult]
    kind: Literal["motion","nav","perception","wait","io"] = "motion"
    weight: float = 1.0          # 进度权重
    timeout: float | None = None
    retries: int = 0
    on_failure: Literal["abort","skip"] = "abort"
    tick_budget: float = 0.1
```

### 与参考实现的差异

| 项 | 参考实现 | 本设计 |
|---|---|---|
| 步骤表达 | `(callable, 描述串)` | `Step` 数据类 |
| `phase` | 复用描述串 | `Step.name` |
| 步骤分类 | 描述串前缀字符串匹配 | `kind` 枚举 |
| 进度 | 无 | `weight` 累加 |
| 单步超时 / 重试 | 无（业务里手写循环） | `timeout` / `retries` + `retryable` |
| 失败策略 | 一律中止 | `abort` / `skip` |
| 动态追加 | `get_extend_actions_list()` | `ctx.append_steps()` |

### 三条硬约束

1. 单次 `run` 不超过 `tick_budget`（默认 0.1s，感知等待类可声明至 2s）
2. `run` 必须可重入（重试时会再次调用）
3. `run` 必须响应取消（不可中断阻塞一律禁止，IO 必须带超时）

### 未采纳

| 方案 | 原因 |
|---|---|
| A 沿用元组列表 | 描述串兼作 phase 与路由键，耦合脆弱 |
| C 协程（`async def run`） | 表达力最强，但与 10Hz 同步循环、急停抢占的融合需重构执行器，收益不足以覆盖风险 |

## D-005 技能能力边界：只依赖 `skill_sdk`，能力经 `StepCtx` 注入

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 技能包只依赖 `core/skill_sdk` 一个公共 API 包，通过 `StepCtx` 获取 `body`/`sensor`/`state`/`cfg` 等抽象能力；不持有具体控制器，不 `import` `core` 实现包 |
| 依据 | 「独立安装 + 可跨机型 + 可脱离真机测试」三者共同要求技能既不知道自己在什么机器人上跑，也不知道运行时长什么样 |

### 依赖方向

```
技能包 ──▶ core/skill_sdk ◀── core/skill_core ──▶ body / sensor / common
   ▲                              │
   └────────── 禁止 import ────────┘
```

`core/` 因此拆为：`interfaces` / **`skill_sdk`** / `common` / `sensor` / `body` / `skill_core`。

### `StepCtx` 契约

| 字段 | 说明 |
|---|---|
| `skill` / `params` | 技能名与本次入参 |
| `cfg` | **仅本技能私有配置段**，看不到其他技能 |
| `globals` | 全局白名单项（`open_nav` / `tick_rate`） |
| `body` | `arm` / `gripper` / `waist` / `head` / `base`，按能力切分而非按机型 |
| `sensor` | `rgbd()` / `transform_to_base()` |
| `state` | `get`/`set`，key 白名单 |
| `log` / `say` / `now` | 结构化日志 / TTS / 可注入时钟 |
| `cancelled` / `check_cancel` | 取消检查，长步骤内部也要调 |
| `append_steps` | 运行时追加步骤 |

### 四条规则

| # | 规则 | 原因 |
|---|---|---|
| 1 | 技能只 `import thinker_skill_sdk` | `core` 重构、Cython 裁剪不影响已安装技能 |
| 2 | `ctx.cfg` 只含本技能配置段 | 参考实现全局 `config` 单例导致跨技能参数污染 |
| 3 | `postcondition` 由 Pipeline 成功后统一写 | 避免"返回成功但状态没写" |
| 4 | 禁止跨 tick 的全局可变状态 | 重试会重入 |

### 约束：`BodyAPI` 必须 tick 友好

所有方法要么幂等、要么可查询完成状态（如 `navigate_to()` 幂等启动 + `arrived()` 查询）。否则技能作者会写出阻塞调用，破坏 D-004 的 tick 契约。

### 未采纳

| 方案 | 原因 |
|---|---|
| 注入具体控制器（参考实现做法） | 换机型必须重写技能；参考实现 7 个控制器注入即此路 |
| 允许 `import` 任意 core 子模块 | 破坏独立安装；Cython 裁剪与版本升级都会碎 |
| `ctx.call("arm.move_to", ...)` 字符串路由 | 无类型检查、无补全、拼错运行时才发现 |

### 收益

- 技能可在开发机用 `FakeBody` / `FakeSensor` 跑通全链路，M0 不依赖真机
- Cython 只需保护 SDK 公共符号
- 技能与 core 依赖面收敛为 1 个包

## D-006 `core` 是封闭集合，业务逻辑留在技能包

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | `core` 只放机器人通用能力，包数量与机器人形态相关、**不随技能数量增长**。业务逻辑留在技能包内，允许与其他技能相似但不共享 |
| 依据 | 业务方原则：不能新增一个技能就在 `core` 下新增子模块 |

### 澄清：三包重复的根因不是业务逻辑

| 重复内容 | 量级 | 归属 |
|---|---|---|
| Pipeline / 控制器 / 感知流水线 / tf / 启动脚本 | 数千行 | `core`（一份） |
| 业务逻辑（目标选择、抓瓶位姿、重试次数、文案） | 百余行 | 技能包（允许重复） |

平台代码重复是灾难，业务逻辑重复是可接受成本 —— 瓶子和箱子的策略本就不同，强行抽象只会产生按物体分支的大函数。

### `core` 准入标准（四条全满足）

| # | 标准 |
|---|---|
| 1 | 与具体技能、物体、场景无关 |
| 2 | 平台自身或多个技能确实需要 |
| 3 | 代码中不出现业务词表（`bottle` / `box` / `drawer`） |
| 4 | 只在既有包内新增函数/类型，**不新增包**（新增包需架构评审） |

### 未采纳

| 方案 | 原因 |
|---|---|
| `core/skill_utils` 存放技能间共享业务逻辑 | 会随技能数量增长而膨胀，违反 `core` 封闭原则 |
| 技能间复制粘贴全部代码 | 平台代码重复是三包原罪 |
| 把相似业务抽象成一个通用函数 | 按物体分支的巨型函数，比两份小函数更难维护 |

### 允许的重复边界

| 情况 | 处理 |
|---|---|
| 两个技能有相似逻辑 | 各自实现 |
| 三个以上技能逐行相同 | 先判断是否"通用能力被写成业务代码"，是则上移 `core` 既有包 |
| 只差参数的同源逻辑 | 逻辑一份在技能包，参数进 `configs/skills/<skill>.yaml` |
| 跨技能组合 | 场景技能通过 Action 编排，不共享代码 |

## D-007 感知算法随技能走，`core/perception` 更名为 `core/sensor`

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 检测、估计、识别等**算法实现一律放在技能包内**，不新增 `algorithms/` 顶层目录，也不收进 `core`；`core/perception` 更名为 `core/sensor`，只承担感知数据通道职责 |
| 依据 | 算法种类发散（几十种），而 `core` 的包数必须收敛；两者直接冲突。参考实现把 10 个检测器塞进 `pose_estimate/detect/`，任何算法变动都要重建整包 |

### 三层归属判据

```
这段逻辑是硬件驱动、数据通道或纯通用工具吗？
├─ 是 → core/body / core/sensor / core/common（只在既有包内加函数）
└─ 否 → 留在技能包（检测、估计、识别等算法与业务逻辑都属此类），
        允许与其他技能相似但不共享
```

| 层 | 放什么 | 数量特征 |
|---|---|---|
| `core/sensor` | 相机订阅、RGB-D 对齐、内参、`cam→base` 变换、时间戳缓冲 | 固定 |
| `core/body` | 控制器、QP、moveit、腰/头/手爪/导航/tf（**已被 D-014 取代：机型实现移至 `robots/`，`core/body` 只留抽象与安全层**） | 固定 |
| 技能包 | 检测器封装、位姿算法、目标选择、业务阈值 | 随技能增长 |
| `weights/` | 模型文件（各技能共享同一份） | 随算法增长 |

### 改名与接口变更

| 项 | 原名 | 新名 |
|---|---|---|
| 包 | `core/perception` / `thinker_perception` | `core/sensor` / `thinker_sensor` |
| Protocol | `PerceptionAPI`（`detect()` / `latest()`） | `SensorAPI`（`rgbd()` / `transform_to_base()`） |
| StepCtx 字段 | `ctx.perception` | `ctx.sensor` |
| 能力声明 | `perception.openset` | `sensor.rgbd` |

改名的理由：算法迁出后它已不是“感知算法容器”，且与技能类别 `skills/perception/`（视觉感知类）同名易混。

**不改名的保留项**：`Step.kind = "perception"`（步骤类型，表示允许较长 `tick_budget`）、`skills/perception/`（技能类别）、Q-009 中的类别边界讨论。

### 配套硬约束

| # | 约束 | 原因 |
|---|---|---|
| 1 | 模型**延迟加载**：装配时不加载权重，首次 `Step.run` 才 `ensure_model()` | 装 N 个技能就有 N 份模型常驻，Jetson 显存撑不住 |
| 2 | 权重统一放 `weights/`，不进技能包 | 避免同一份 GroundingDINO 被复制多份 |
| 3 | 技能自带算法必须是**纯函数库**：不装配节点、不订阅话题 | 维持“技能包不含节点装配”的边界 |
| 4 | 检测封装允许重复，但要薄（十几行调用第三方库） | 控制重复成本；若真出现三份逐行相同，再回判是否属通用能力 |

### 未采纳

| 方案 | 原因 |
|---|---|
| 新增 `algorithms/` 顶层目录，算法一包一个 | 增加第四类可安装单元，部署与依赖管理复杂化；业务方明确否决 |
| 算法全部收进 `core/perception` | `core` 会随算法数量膨胀，封闭集合原则失效 |
| 保留 `core/perception` 名字只改描述 | 与技能类别 `perception/` 同名，且名字已不反映实际职责 |

## D-010 身体释放与抢占：主动有序交接，看门狗仅兜底

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-11） |
| 结论 | 身体租约的释放与抢占走主动有序路径，看门狗/TTL 只负责异常兜底 |
| 依据 | 看门狗/TTL 只是被动兜底；正常场景需主动释放与有序抢占，否则交接可能停在半空位姿 |

### 租约生命周期

```
free ──acquire(能力, ttl)──▶ held
held ─┬─ 正常完成/失败/取消 ─▶ 软急停 ─▶ 停稳确认 ─▶ release ─▶ free
      ├─ 抢占(preempt)     ─▶ 软急停旧 ─▶ 停稳确认 ─▶ 交接给新 ─▶ held(新)
      ├─ 紧急抢占          ─▶ 立即停止(不等停稳) ─▶ 交接 ─▶ held(新)
      ├─ 看门狗超时         ─▶ 软急停 ─▶ release ─▶ free（被动兜底）
      └─ TTL 未续约        ─▶ release ─▶ free（被动兜底，防进程崩溃）
```

### 四条硬约束

1. 释放必须停稳确认：`stop → is_moving == false → release`
2. 抢占 = 有序交接，任何时刻身体只有一个真正控制者
3. 续约自动化：TTL 由 Pipeline 每 tick 自动续，技能作者无感知
4. 抢占分级：普通抢占走停稳流程；急停/安全事件的紧急抢占立即停止

## D-015 能力契约：能力 + 机型 + 版本

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-12） |
| 结论 | 技能声明「能力 + 参数约束」与「机型/版本兼容」，机型声明「能力提供」，装配期做子集匹配 |
| 依据 | 技能需跨机型复用，但不同机型的自由度、手爪类型、相机路数不同 |

### 技能侧 `skill.yaml`

```yaml
requires:
  body.arm:     {dof: ">=6"}
  body.gripper: {type: any, dof: ">=6"}
  sensor.rgbd:  {count: ">=1"}
compatible:
  robot_models: [tienkung_dex]
  min_robot_version: "3.0"
```

### 机型侧 `capabilities.yaml`

```yaml
robot_model: tienkung_dex
version: "3.0"
capabilities:
  body.arm:     {dof: 7, reach: 0.7}
  body.gripper: {type: brainco, dof: 6}
  sensor.rgbd:  {count: 4, depth_unit: mm}
```

### 匹配规则

- 装配期校验：`requires ⊆ capabilities`、机型兼容、版本满足，否则**跳过并告警**（不阻塞其他技能）
- v1 只校验「能力名 + `robot_models` + `min_robot_version`」；参数约束（`dof`/`reach`/`type`）的匹配器 v1.1 启用

### 手部变体（同一机型多配置）

同一机型可能配不同手部，技能需按手部类型匹配。以 `tienkung_dex` 为例：

| 变体 | `hand_vendor` | 启用 `hand` 子系统 | `body.gripper` |
|---|---|---|---|
| `brainco` | `brainco` | 是 | `{type: brainco, dof: 6}` |
| `inspire` | `inspire` | 是 | `{type: inspire, dof: 13}` |
| `fixed`（拳头假手） | — | 否 | **不存在** |

落地方式：

- 机型侧用 `capabilities.yaml` 的 `hand_variants` 表达；
- 运行期由 `configs/robot.yaml` 的 `hand_variant` 选择；
- 装配期合并「基础能力 + 所选变体能力」后做子集匹配；
- 技能用 `requires.body.gripper.type` 约束（`brainco` / `inspire` / `any`）；
- 拳头假手下无 `body.gripper`，依赖它的技能自动跳过并告警。

## D-017 臂 IK 选型：QP + DAQP，放 `robots/<model>` 内部

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-12） |
| 结论 | 臂位姿 IK 采用「每步 QP（最小二乘 + 阻尼 + 关节限位）」形式，求解器主选 **DAQP**（dual active-set）；实现放 `robots/<model>/ik.py`，作为 `move_to_pose` 的内部策略；**不封装为技能** |
| 依据 | 1) IK 是"求解中间量"而非"用户任务"，不应暴露 MCP/Action；2) 算法多样用 Strategy（`configs/robot.yaml` 的 `ik.solver`）；3) tienkung_dex 臂展仅 0.52m，抓取目标常在限位边界，DLS 会卡住而 DAQP 能解 |

### 为什么不是技能

| 维度 | 技能 | IK |
|---|---|---|
| 面向 | 用户 / Agent | 平台内部 |
| 接口 | MCP tool / Action | 无（内部） |
| 依赖方向 | 依赖 `skill_sdk` | 被 `body` 依赖（不能反向） |
| 可替换 | 技能间互不替换 | 算法可替换（Strategy） |

### 为什么是 DAQP 而非纯 DLS（实测）

左臂、base 系、`pelvis_height=0.92`：

| 目标 | DAQP | DLS |
|---|---|---|
| `(0.30, 0.20, 0.90)` 可达 | **0.74 mm ✅** | 14.5 mm ❌ |
| `(0.35, 0.15, 0.85)` 超臂展 | 32 mm（最近解） | 32 mm |
| `(0.40, 0.15, 0.85)` 超臂展 | 65 mm（最近解） | 65 mm |

DLS 在限位处截断后无法收敛；DAQP 把限位作为约束，一步解出最优增量。

### 实现

- `robots/tienkung_dex/ik.py`：URDF 链解析 + 数值雅可比 + `_solve_dls` / `_solve_daqp`
- `body.py`：`TienkungDexArm.move_to_pose` 调 IK，不收敛抛 `RuntimeError`
- `capabilities.yaml`：`body.arm.pose_ik: true`、`ik_solver: daqp`
- `configs/robot.yaml`：`ik.solver / tol / max_iter / damping`
- 依赖：`daqp`（MIT、零传递依赖、有 linux-aarch64 wheel）；缺失时自动降级 `dls`

### 未采纳

| 方案 | 原因 |
|---|---|
| IK 作为技能 | 依赖方向反、语义错、调用链怪 |
| pinocchio | aarch64 需编译 C++，SDK 无此依赖 |
| CCD / FABRIK | 精度不足 |
| 学习型 IK | 需训练数据 |
| 纯 DLS | 限位边界不收敛（实测 14.5mm） |

## D-019 跨技能调用：`ctx.call_skill` 进程内，替代原 Action 方案

| 项 | 内容 |
|---|---|
| 状态 | 已定（2026-11-12） |
| 结论 | 场景技能调用其他技能走 `StepCtx.call_skill(name, params)`（进程内同步执行完整 `runtime.execute`），不走 ROS Action |
| 依据 | 技能层必须保持零 ROS 依赖（D-005）；同进程下 Action 的隔离收益有限；`call_skill` 仍走完整租约 + pipeline + 状态写回 |

### 与原设计（D-006）的差异

| 维度 | 原方案（Action 跨进程） | 现方案（`call_skill` 进程内） |
|---|---|---|
| 技能依赖 | 需 ROS Action client | 只依赖 `skill_sdk` |
| 故障隔离 | 子技能崩溃不拖垮父技能 | 子技能异常由 pipeline 收敛 |
| 复杂度 | 高（异步 / 超时 / 取消传播） | 低 |
| 租约 | 各自申请 | 各自申请（同一 arbiter） |

### 语义

- 子技能未安装 → `INPUT_UNSUPPORTED_COMMAND`，父技能失败
- 子技能执行期间父技能阻塞（`tick_budget` 需覆盖子技能耗时）
- 子技能的 `postcondition` 正常写回共享 `StateStore`
